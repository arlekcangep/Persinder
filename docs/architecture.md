# Архитектура Persinder

> Черновик. Описывает принятые решения и их обоснование. Раздел «Открытые вопросы»
> перечисляет то, что ещё не зафиксировано.

## 1. Назначение

Persinder — поисковый движок для персональной базы знаний. Индексирует и делает
доступным для поиска:

- заметки Obsidian;
- локальные файлы: PDF, DOCX, изображения, DjVu, ZIP;
- веб-материалы.

Виды поиска: по совпадению слов, по тэгам, семантический. Плюс авто-каталогизирование
закладок, книг, статей и CD-архивов.

## 2. Требования и ограничения

- **Переносимость.** Данные и индексы должны легко перемещаться между устройствами.
- **Ноль ресурсов в простое.** Никаких фоновых серверов и демонов.
- **Android обязателен** (позже), десктоп — первый.
- **Десктоп — Windows и Linux** (обе платформы целевые). Кроссплатформенность
  учитывается с самого начала: пути через `pathlib`, регистр имён, кодировка UTF-8,
  атомарные операции файловой системы (`os.replace`), запуск сервиса по требованию
  без фоновых демонов.
- **Только open-source** компоненты.
- **Иерархия поиска.** Результаты группируются по источникам: личное → локальное →
  закладки и web. У каждой группы свой бюджет латентности.
- **Репликация.** Между двумя ПК и мобильными устройствами, включая офлайн-использование.
- **Языки.** Русский и английский обязательно; желательно также другие (особенно китайский).
- **Настраиваемые области.** Локальные папки сопоставляются с ролью в конфиге (см. §6.3).
- **Удаление (высокий приоритет, входит в первый прототип).** Удалённый элемент должен
  исчезать из всех индексов и из результатов поиска (см. §9.1).

## 3. Ключевые принципы

1. **Всё встраиваемое, без сервера.** Никаких процессов в простое.
2. **Иерархия вместо универсальной БД.** Разные группы обслуживаются разными структурами
   индекса, потому что «мгновенный личный поиск» и «миллионы книг» требуют разного.
3. **Производные данные не реплицируются вручную — их либо пересобирают локально,
   либо везёт Syncthing как сайдкары.** Индекс — детерминированная функция от
   (контент + модель эмбеддингов), поэтому никогда не является единственной копией.
4. **Транспорт делегируется Syncthing, семантика (мерж, GC, версии модели) — наша.**
5. **Живая БД никогда не лежит в синхронизируемой папке.**

### 3.1 Чистая архитектура: слои и модели

Соблюдаем **Clean Architecture**: зависимости направлены внутрь, к домену. Домен не
знает ни про HTTP, ни про SQLite, ни про конкретную модель эмбеддингов.

**Слои (снаружи внутрь):**

| Слой | Что это | Примеры в Persinder |
|---|---|---|
| Адаптеры (интерфейсы) | транспорт и хранилища | HTTP (`api`), SQLite (`store`), файловое хранилище текста, читатели сайдкаров |
| Приложение (use cases) | сервисы-сценарии | `ingest`, `embed`, `sources`, `search` |
| Домен (ядро) | чистые сущности и правила | `Area`, `Document`, `Chunk`, идентификаторы |

**Правило: у каждого слоя — свои модели.** Модели для БД, для HTTP и внутренние
модели сервисов разделяются, а не сводятся в один общий `models.py`.

- **Доменные модели** (ядро) — чистые типы без зависимостей: сущности и значения,
  инварианты. Живут в доменном пакете.
- **Модели базы (persistence)** — записи/строки SQLite (колонки, типы, `nullable`).
  Живут внутри модуля-хранилища и наружу не выносятся.
- **Модели HTTP (transport/DTO)** — форма запроса/ответа конкретного эндпоинта
  (`/ingest`) и правила сериализации JSON. Живут внутри `api`.
- **Внутренние модели сервисов** — входы/выходы/задачи конкретного сценария (например,
  `IngestRequest`/`IngestResult`, элемент очереди эмбеддингов). Живут в своём сервисе.

**Запрещено:**

- один общий `models.py` на весь проект;
- импорт DTO или DB-моделей из домена и из чужого слоя;
- отдача DB-записи напрямую как HTTP-ответ (и наоборот).

**Переход между слоями — только через явные мапперы** (`to_domain`, `from_domain`,
`to_dto`). Слои общаются через **порты** — `Protocol`-интерфейсы (см. `docs/modules.md`),
а не через конкретные типы чужих слоёв.

## 4. Источники результатов

Результаты **не сводятся в один общий ранжированный список с весами** — для персонального
поиска кросс-источниковое ранжирование не нужно. Они выдаются **тремя отдельными
группами**:

| № | Группа | Объём | Бюджет латентности | Примечание |
|---|---|---|---|---|
| 1 | Личное | тысячи–сотни тысяч фрагментов | миллисекунды | заметки Obsidian, локальные заметки |
| 2 | Локальное | миллионы | секунды, щедрый бюджет | книги, статьи, архивы |
| 3 | Закладки + web | ∞ | асинхронно, eventual | закладки и веб-материалы |

Группы 1 и 2 отвечают сразу; группа 3 — асинхронно и потоково. Каждая группа
показывается **своим блоком**; между группами порядок не пересчитывается.

Внутри одной группы порядок такой:

1. **Точные совпадения** — дословное совпадение запроса с заголовком, идентификатором
   (DOI, ISBN, arXiv), цитатой.
2. **Семантические** результаты.
3. **Морфологические** (по словам).
4. **По тэгам**.

Точные совпадения стоят выше всего, чтобы не терять буквальные попадания (DOI, название
книги, редкий термин). Тэги при этом могут работать и как фильтр выдачи.

Группы задаются конфигом областей (см. §6.3): «Личное» ← папки роли `personal`;
«Локальное» ← папки роли `foreign` (копии чужого); «Закладки + web» ← хранилище
закладок и папка роли `web`.

## 5. Слои данных

| Слой | Природа | Где живёт | Репликация |
|---|---|---|---|
| Источник (PDF, EPUB, DjVu, ZIP, заметки) | immutable-ish | Syncthing-папки | Syncthing |
| Тэги заметок Obsidian | внутри заметок | Syncthing-папки | Syncthing |
| Сайдкары эмбеддингов (1 на файл) | производное, immutable | `.persinder/` рядом с источником | Syncthing |
| Метаданные элементов (тэги, идентификаторы, коллекции) | sidecar-файл (CSL-JSON) | рядом с источником | Syncthing |
| Локальный ANN-индекс | производное | локально, вне синка | пересборка |
| SQLite (FTS5, тэги, id↔vector) | производное | локально, вне синка | пересборка |

Правило: **всё, что выводимо из источника или сайдкаров, локально и пересобираемо;
синхронизируется только то, что иначе потеряется.**

## 6. Источник данных и Syncthing

Syncthing уже реплицирует волт Obsidian и локальные папки — в том числе ради
офлайн-доступа. Поэтому он принимается как **штатный слой репликации источника**,
и дублировать его своим хранилищем не нужно.

Индексер смотрит на эти папки как на источник. Единственная запись, которую он туда
производит, — сайдкары (см. §7) и sidecar-файлы метаданных элементов (см. §7.1).

### 6.1 Obsidian

- **Тэги остаются внутри заметок** (`#tag` в теле или во frontmatter) и остаются
  каноническим источником. Приложение не ведёт параллельного хранилища тэгов для
  заметок — оно их **извлекает** при индексации.
- Связи заметок, вложения, `.obsidian/` — обычные файлы в Syncthing-папке.
- Сайдкары складываются в скрытую точку-папку, чтобы не мусорить в проводнике
  Obsidian и не мешать его собственному индексированию.

### 6.2 Локальные файлы

- PDF/DOCX/DjVu/ZIP/изображения индексируются из тех же Syncthing-папок.
- ZIP и CD-архивы раскрываются рекурсивно.
- Для файлов, где тэги негде хранить, они живут в sidecar-файле метаданных (см. §7.1).

### 6.3 Области (роли папок)

В конфиге перечисляются локальные папки с указанием назначения:

```yaml
areas:
  - path: ~/Obsidian/Personal
    role: personal
  - path: ~/Obsidian/Work
    role: personal
  - path: ~/Library/Books
    role: foreign      # копия чужого: книги, статьи
  - path: ~/Articles
    role: foreign
  - path: ~/WebArchive
    role: web          # наполняется отдельным проектом-скрапером
```

Роли:

- `personal` → группа «Личное»;
- `foreign` → группа «Локальное» (копии чужого);
- `web` → группа «Закладки + web».

Телефон в per-device ignore patterns игнорирует папки ролей `foreign` и `web`.

### 6.4 Watcher (модуль `sources`)

**Технология — гибрид (D20):**

- **Polling-скан (stdlib)** — источник правды индексации. Периодический обход областей
  со снапшотом `(size, mtime_ns)` и диффом. Работает везде, включая сетевые шары и
  vboxsf, где нативные события ненадёжны.
- **`watchdog` (опциональный extra `watch`)** — ускорение: события inotify /
  `ReadDirectoryChangesW` дают низкую латентность на локальных ФС. Не источник правды:
  события только триггерят внеплановый скан.

**Журнал наблюдения (D21).** Состояние watcher'а хранится в журнале
`data_dir/journal.jsonl` — append-only, одна строка — один переход, лежит рядом с БД
и читается глазами/grep'ом. Отдельного файла-снапшота нет: последняя запись по файлу
и есть его состояние. Цепочка статусов:

```
discovered → sent → indexed | duplicate | rejected | error
                 ↘ skipped (формат не обслуживается / нет текста)
deleted
```

- `discovered`/`sent` — **незавершённые** состояния: если процесс упал между сканом и
  `ingest`, файл при следующем запуске обрабатывается заново (в дифф такие файлы не
  попадают). Также поэтому файл, пропущенный debounce'ом в одном проходе, ловится
  следующим.
- `deleted` фиксируется после чистки индекса; `detail` поясняет, что стало с
  документом (вычищен целиком / сохранён, пока жив другой источник / отсутствовал).
- Битые строки (обрыв при аварии) при чтении пропускаются — журнал самовосстанавливается.
- **Обрезка**: при запуске `watch` (`Journal.compact`) удаляется история старше
  `JOURNAL_RETENTION_DAYS` (60 дней); последнее состояние каждого файла хранится
  всегда, поэтому давно не менявшиеся файлы не переиндексируются.

**Конфиг** (YAML, PyYAML; extra `config`):

```yaml
areas:
  - path: ~/Obsidian/Personal
    role: personal

watch:
  poll_interval: 30     # сек между сканами
  debounce: 2           # сек — ждать после mtime, чтобы не читать полуфайл
  ignore:               # дополнительно к встроенным паттернам
    - "**/drafts/**"
```

**Встроенные ignore-паттерны** (служебное и производное, не индексируется):
`.obsidian/`, `.persinder/` (сайдкары), `.stfolder/`, `*.sync-conflict-*`,
`.syncthing.*.tmp` — Syncthing пишет файл во временный файл и переименовывает.

**Интерфейс:** сканер выдаёт `ScanResult` с событиями `created / modified / deleted`
(пути относительно области + роль), события отдаются в `ingest`. Watcher запускается
приложением по требованию (D1), не демон.

**Экстракторы и форматы.** Какая область что индексирует — белый список имён
экстракторов `formats` (пусто — область пропускается). Экстракторы делятся на
обычные (файл → один результат: `markdown`, `text`, `html`, `mhtml`,
`pdf` (extra `pdf`)) и **контейнеры** (файл → несколько частей). **`archive`** —
контейнер форматов zip, 7z (extra `7z`), tar (+ tar.gz/tgz/tar.bz2/tar.xz —
распаковываются за один шаг) и rar (extra `rar` + внешний unrar/7z/bsdtar):
каждая поддерживаемая запись становится отдельным документом
(`bundle.zip/inner.md`); экстрактор для записи контейнер берёт у фабрики
области (набор разрешённых форматов у разных каталогов свой). Вложенные
архивы раскрываются **на один уровень** (`a.zip/inner.zip/file.md`), глубже —
нет (защита от бомб); tar.gz — один контейнер, промежуточного уровня не
создаёт. Одиночный `.gz` — один файл без суффикса `.gz`. Неподдерживаемые
форматы и слишком большие записи пропускаются; лимиты по числу записей /
размеру записи / суммарному размеру — защита от бомб. Удаление файла-контейнера
убирает из индекса и его части. Виртуальные части (данных на диске нет)
хранятся как сайдкары в `data_dir/virtual`. Остальные форматы (EPUB/DjVu/OCR/
DOCX/изображения) — новые реализации порта `Extractor` или `ContainerExtractor`.

## 7. Сайдкары эмбеддингов

**Один сайдкар на один исходный файл и одну модель** (а не на чанк). Это критично:
Syncthing плохо переносит огромное число мелких файлов; у файла могут одновременно
жить сайдкары нескольких моделей — по подпапке на модель (миграция, D24):

```
vault/
  books/
    DeepLearning.pdf
    .persinder/
      e5-small-int8-v1/DeepLearning.pdf.pdr   ← сайдкар активной модели
      placeholder-v1/DeepLearning.pdf.pdr     ← старый, пока модель не удалена
```

Содержимое сайдкара:

- **отпечаток модели**: id, версия, размерность, тип квантования (f16/int8) — обязателен;
- параметры чанкинга;
- чанки: диапазон в тексте (offset/length), вектор.

Свойства:

- Сайдкар — **кэш**, безопасный к игнорированию: нет сайдкара — эмбеддинги считаются
  локально.
- Записывается **атомарно** (временный файл рядом → `rename`); `.persinder/`
  целиком игнорируется индексацией (D20, встроенные ignore-паттерны).
- Сайдкар без источника удаляется **инлайн** там же, где удаляется текст
  (D24): правка перезаписывает его на новом документе, удаление убирает вовсе.
  Отдельного GC сирот сайдкаров нет.
- **Удаление модели удаляет все её сайдкары** (файловые и виртуальные) в один
  момент вместе с весами — не раньше: другие устройства могут ещё работать со
  старой моделью (`persinder model remove`, D24).
- Размер сайдкара книги — единицы МБ; «монолита библиотеки» не возникает.
- Извлечённый текст в сайдкар **не кладётся** (дублирует источник, раздувает синк).

### 7.1 Сайдкар метаданных элемента

Для не-заметок (книги, статьи, web) пользовательские метаданные живут в отдельном
sidecar-файле рядом с элементом. Формат — **готовый стандарт CSL-JSON** (тот же, что
использует Zotero), плюс небольшой блок полей Persinder:

```json
{
  "citation": {
    "type": "book",
    "title": "…",
    "author": [{"family": "…", "given": "…"}],
    "issued": {"date-parts": [[2016]]},
    "DOI": "10.1000/xyz",
    "ISBN": "978-…",
    "keyword": "machine learning, neural networks"
  },
  "persinder": {
    "tags": ["nlp", "read-later"],
    "collections": ["Книги по ML"],
    "progress": 0.35,
    "source_area": "foreign"
  }
}
```

- **Идентификаторы** (DOI, ISBN, ISSN, arXiv, PMID) вытягиваются из самих книг и статей
  при разборе и складываются сюда же.
- Формат стандартный и текстовый → хорошо мержится в Syncthing и читается человеком.
- Тэги заметок Obsidian в этот формат не переезжают (они остаются внутри заметок, §6.1);
  объединение с тэгами заметок происходит на этапе запроса.

## 8. Локальные производные

Не синхронизируются, пересобираются на каждом устройстве из источника и сайдкаров.

- **SQLite**: метаданные, FTS5 (поиск по словам), материализованные тэги, сопоставление
  `id ↔ vector`, перекрёстные ссылки. Расширения: **sqlite-vec** для личного слоя.
- **Векторы чанков в самой SQLite** — таблица `embeddings`
  `(id, model, doc_id, chunk_index, vector f16, UNIQUE(model, doc_id, chunk_index))`.
  Её материализует воркер `embed` из сайдкаров/напрямую при расчёте (в одну
  транзакцию с сайдкаром), удаляет `ingest` каскадом по документу (FK ON DELETE
  CASCADE) и `model remove`. `id` — стабильный ключ строки: по нему ANN-индекс
  ссылается на чанк, upsert вектора не меняет `id`, так что «таблица ↔ индекс»
  сходятся по ключу.
- **ANN-индекс (USearch)** — движок векторного поиска (модуль 3, §9). Один
  mmap-файл на модель: `data_dir/ann/<модель>.usearch`, метрика — косинус
  (USearch отдаёт `distance = 1 - cos`, наружу — `score = 1 - distance`).
  Ключи — стабильные `id` строк `embeddings`. Индекс — производное: ведёт его
  воркер `embed` (добавляет векторы сразу при расчёте, в конце прохода
  реконсилирует протухшие ключи), а `persinder ann rebuild` пересобирает из
  таблицы (холодный старт устройства). Если файла индекса нет, `VectorSearch`
  падает на точный скан таблицы — тот же результат, медленнее на больших объёмах.
  Дубликат ключа `add` пропускает (инвариант «ключ неизменяем»: `doc_id` — хэш
  содержимого). На будущее (Android, большие коллекции): тот же USearch, файлы
  `mmap`, при необходимости — шардирование по коллекциям.

## 9. Конвейер индексации

Стадии и типичные задержки (десктоп):

| Стадия | Задержка |
|---|---|
| Syncthing заметил файл | ~10 с (fs-watcher), до часа при полном рескане |
| Наш watcher увидел файл | мгновенно (после rename из `.syncthing.*.tmp`) |
| Извлечение текста (PDF/EPUB) | 1–10 с |
| Извлечение текста (DjVu/OCR) | минуты |
| Чанкинг | мс |
| Эмбеддинги (если нет сайдкара) | **узкое место**: 10–60 с на книгу на CPU |
| Вставка в ANN (HNSW) | мс–секунды |
| Атомарный swap сегмента | мс |

Итог по типам контента:

| Что добавилось | Появится в поиске |
|---|---|
| Заметка Obsidian | секунды (почти мгновенно) |
| Статья / небольшой PDF | секунды |
| Книга ~300 страниц | ~10–60 с (или мгновенно при готовом сайдкаре) |
| Скан / OCR / DjVu | минуты |
| Пакет из 100 книг | минуты–часы; прогрессивно |

Механизмы ускорения и предсказуемости:

1. **Прогрессивная индексация**: имя/метаданные/тэги → FTS5 → векторы.
2. **Приоритетная очередь**: личное и недавно открытое вперёд, массовый импорт — в фон.
3. **Дедупликация по хэшу** файла и по отпечатку сайдкара.
4. **Инкрементальные сегменты**: новая книга = новый маленький сегмент, без полной
   перестройки.
5. **Кэш эмбеддингов** из сайдкаров: холодное устройство не гоняет модель заново.

### 9.1 Инкрементальные удаления и правки

> **Приоритет: высокий.** Удаление входит в первый прототип. Правки — сразу за ним.

Элемент опознаётся ключом `(область, относительный путь)` и хэшем содержимого.

- **Создание**: разбор → sidecar метаданных → FTS5 → векторы → новый сегмент.
- **Правка**: изменился хэш содержимого → переразбор и переэмбеддинг элемента,
  перезапись его записей (старые удаляются, новые вставляются).
- **Удаление**: приходит из Syncthing → удаляются строки в SQLite и из FTS5, ключи
  вектора помечаются `tombstone` в сегменте, сайдкары удаляются.
- **Переименование/перемещение**: опознаётся по хэшу содержимого → меняется только
  путь, переэмбеддинг не нужен.
- **Компакция**: фоновое слияние сегментов, при котором `tombstone`-записи выпадают.
  Полная перестройка индекса не требуется.
- **Конфликты Syncthing** (`*.sync-conflict-*`) обрабатываются как отдельные элементы,
  а метаданные сливаются по правилу объединения.

**Статус в прототипе (морфологический слой, без векторов).** Ключ элемента —
`(область, относительный путь)`, документ — хэш текста. У файла **один источник**:
при правке разбирается новый текст, и его документ вытесняет прежний
(`_bind_source` в сторе) — прежний документ вычищается, если у него не осталось
**других** источников (тот же текст может быть в другом файле). Удаление убирает
источник, а документ — когда источников не остаётся (D13). Журнал наблюдения (D21)
фиксирует цепочку `discovered → … → deleted` по каждому файлу.

Сырой текст удаляется вместе с документом **сразу** (D22): и правка, и удаление
идут через `IngestService`, у которого оба порта. Краш в окне «записали текст —
не закоммитили документ» подчищает **журнал вызовов ingest** (D23): на старте
сервис сам смотрит незавершённые вызовы и убирает брошенный текст, а watcher при
следующем скане пришлёт файл заново (в его журнале по файлу нет ответа).

**Векторный слой в прототипе (модуль `embed`, D24).** Модель управляется явно
через реестр (`persinder model ...`): установка (`install <ключ>`, скачивание весов
в `<home>/models/<ключ>/` — корень `Settings.models_dir`),
переключение поиска (`use <ключ>`), удаление вместе с сайдкарами (`remove <ключ>`).
Два хендла на профиль (`data_dir/models.json`): `embedding` — какой моделью считаем
новые/изменённые файлы, `search` — какой моделью ищем. Воркер по требованию
(`persinder embed`) разбирает очередь эмбеддингов и пишет **сайдкары** (§7):
реальному файлу — рядом (`.<каталог>/.persinder/<модель>/<файл>.pdr`),
виртуальному (нет пути) — в `data_dir/virtual/<модель>/<doc_id>.pdr`. Сайдкар
удаляется вместе с текстом (правка/удаление — через `ingest`). Эмбеддер — заглушка
(`placeholder-v1`, встроена) или реальная e5-small (ONNX INT8) — фабрика
`build_embedder(ключ)` по задачам очереди, поэтому в одном проходе уживаются
задачи разных моделей (миграция).

**Векторный поиск (модуль 3, `vectorindex`).** Реализован поверх связки
SQLite + USearch (§8): воркер материализует векторы чанков в таблицу `embeddings`
(по модели) и ведёт ANN-индекс `data_dir/ann/<модель>.usearch`; `VectorSearch`
считает эмбеддинг запроса (префикс `query:`, §12.1) активной поисковой моделью
(`state.search`), ищет top-k по косинусу в индексе, сопоставляет ключи с таблицей
(протухшие отсекаются) и падает на точный скан, если индекса нет.
`persinder ann rebuild` пересобирает индекс из таблицы (холодный старт/рассинхрон).
В ответе поиска семантические хиты — отдельным полем `semantic_hits` рядом с
морфологическими `hits`; объединение в единый рейтинг (D16) — следующий шаг.

## 10. Репликация

| Что | Кто везёт | Семантика на нас |
|---|---|---|
| Источник и заметки | Syncthing | — (тэги заметок уже внутри) |
| Сайдкары эмбеддингов | Syncthing | версии модели, GC |
| Метаданные элементов | Syncthing (sidecar-файлы) | слияние конфликтов |

- **Метаданные элементов** для не-заметок (тэги, коллекции, прогресс) — маленькие
  sidecar-файлы CSL-JSON (§7.1). Syncthing их везёт; при появлении `*.sync-conflict-*`
  приложение сливает по правилу объединения (для тэгов — union).
- **Живой SQLite в Syncthing-папку не кладём** — только файлы.
- **Per-device ignore patterns**: телефон игнорирует сайдкары областей `foreign`/`web`,
  чтобы не тянуть весь тяжёлый локальный слой.
- Syncthing versioning (staggered) можно использовать для восстановления повреждённых
  сайдкаров.

## 11. Мобильные устройства (Android)

- На телефон уезжает только **личный слой + метаданные** (и, при желании, «избранное»).
- Полный индекс локального слоя на миллионы статей на телефоне **не строится**.
- Эмбеддинги для нужного подмножества приходят из сайдкаров через Syncthing.
- Фоновая индексация ограничена Doze: запускать «на зарядке + Wi-Fi» или по требованию.
- Векторный движок — тот же **USearch** (официальные Android `.so` + JNI).

### 12.1 Модель эмбеддингов

Требование: **русский и английский обязательно, желательно китайский**. Плюс — важное
следствие из §7: раз сайдкары общие (у файла лежат эмбеды нескольких моделей,
D24) и модель можно сменить явно, **модель должна запускаться и на десктопе, и на
Android**. Это отсекает тяжёлые модели как «единую для всех».

| Модель | Параметры | Размерность | Макс. токенов | Языки | Лицензия | Вес INT8 | Мобильность |
|---|---|---|---|---|---|---|---|
| multilingual-e5-small | 118M | 384 | 512 | 100+ (ru/en/zh) | MIT | ~120 МБ | отличная |
| multilingual-e5-base | 278M | 768 | 512 | 100+ | MIT | ~265 МБ | средняя |
| multilingual-e5-large | 560M | 1024 | 512 | 100+ | MIT | ~535 МБ | тяжёлая |
| gte-multilingual-base | 305M | 768 | 8192 | 70+ | Apache-2.0 | ~305 МБ | средняя |
| bge-m3 | 568M | 1024 | 8192 | 100+ | MIT | ~570 МБ | тяжёлая |
| Qwen3-Embedding-0.6B | 596M | 1024 (MRL) | 32768 | 100+, сильный zh | Apache-2.0 | ~600 МБ | тяжёлая |
| EmbeddingGemma 300M | 308M | 768 (MRL до 128) | 2048 | 100+ | Gemma Terms* | ~300 МБ | отличная |

\* Лицензию нужно проверить: по разным источникам встречается и Gemma Terms, и Apache-2.0.

Кратко о характеристиках:

- **Параметры** — «размер мозгов» модели. Больше — обычно точнее, но тяжелее и медленнее.
- **Размерность** — длина вектора на фрагмент. Прямо влияет на размер сайдкара и скорость
  поиска: 1024 против 384 — примерно в 2,7 раза больше данных.
- **Макс. токенов** — какой длины кусок текста влезает за раз. У `e5` всего 512, у Qwen3 —
  32k. Для книг это решается нарезкой на чанки, но длинный контекст упрощает.
- **Префиксы**: `e5` требует приписки `query:` к запросу и `passage:` к тексту, иначе
  качество падает.

**Базовый вариант:** `multilingual-e5-small` — единая модель для десктопа и Android.
Покрывает ru/en/zh, MIT, самый маленький сайдкар (384), уверенно живёт на телефоне.

Модель управляется явно — реестр и хендлы (D24). Каждая модель — подпапка в
каталоге приложения `<home>/models/<ключ>/` (веса + токенизатор; корень —
`Settings.models_dir`; отдельного глобального каталога не вынесено).
Заглушка `placeholder-v1` встроена (та же размерность 384) — работает, пока
реальная не установлена. Установка (`persinder model install <ключ>`) скачивает
веса с HuggingFace (только stdlib, на Windows без Docker), переключает `embedding`
на новую модель и ставит в очередь пересчёт всех источников — миграция стартует
**сразу при install**, а не при `use`. Переключение поиска — отдельная ручка
(`persinder model use <ключ>`): к этому моменту по новой модели уже должны быть
пересчитаны существующие файлы. Пока `embedding ≠ search`, новые файлы считаются
**обеими** моделями — поиск на старой не теряет свежие документы. Удаление
(`persinder model remove <ключ>`) убирает веса и все сайдкары модели в один момент
(не раньше — другие устройства могут быть ещё на старой модели), активные модели
удалить нельзя.

**Резерв:** если качества по китайскому или сложным запросам не хватит —
`Qwen3-Embedding-0.6B` (лучший из «маленьких», Apache-2.0, 32k контекст), но он тяжёл для
телефона: тогда либо телефон не потребляет общие сайдкары, либо нужна квантованная сборка.

Пример размера сайдкара: книга на 1000 фрагментов при 384 измерениях и квантовании f16 —
около 0,8 МБ; при 1024 измерениях — около 2 МБ.

### 12.2 Русскоязычный поиск по словам

Встроенный FTS5 нормально **не стеммит русский** (`porter` — только английский). Решение:

- Перед записью в FTS5 текст **нормализуется и стеммится** (Snowball для ru и en);
  в индексе хранятся уже стеммированные токены, запрос нормализуется так же.
- Snowball лёгкий и портируемый: на десктопе — Python (PyStemmer/nltk), на Android —
  Lucene Snowball или тонкая JNI-обёртка.
- Лемматизация `pymorphy3` даёт точнее, но она Python-only → годится только для
  десктопного индекса, не для общего кэша.
- **Китайский** требует сегментации (CJK): отдельный токенизатор (`jieba` на десктопе,
  ICU на Android) — как расширение на будущее.

### 12.3 Веб и закладки — отдельный проект

Скрейпинг веба — **отдельный проект** (свой функционал, свой цикл разработки). Он
сохраняет контент в папку роли `web`, а Persinder его просто подхватывает.

- Старт: простой скрейпер — тянем то, что отдаётся статически.
- Динамические страницы (скрипты) — позже, отдельными коннекторами к популярным ресурсам.
- Интерфейс между проектами — папка `web` + sidecar метаданных (§7.1).
- Источник закладок пока не определён (см. §14).

### 12.4 Шифрование

Пока **не делаем**: Obsidian из коробки не шифрует, так что локальная БД шифрованием
не выделяется. Вернуться к вопросу позже (например, SQLCipher).

## 13. Риски и меры

| Риск | Мера |
|---|---|
| Смена модели эмбеддингов ломает всю библиотеку | сайдкар на модель (D24): старые живут рядом до `model remove`; миграция по явному `install` → `use`, поиск на старой до переключения |
| Гигантский монолитный индекс | шардинг по коллекциям, immutable-сегменты, атомарный swap |
| Повреждение индекса | индекс пересобираем, никогда не единственная копия |
| Порча из-за синка живой БД | БД всегда вне Syncthing-папки |
| Churn мелких файлов в Syncthing | один сайдкар на файл, не на чанк |
| Конфликты Syncthing | app-level слияние `*.sync-conflict-*` |
| Ограничения фона на Android | индексация на зарядке/Wi-Fi, только личный слой |
| Общая модель не запускается на Android | выбирать модель, совместимую с мобильным рантаймом (§12.1) |
| Русская морфология не покрыта FTS5 | предварительный стемминг перед записью (§12.2) |

## 14. Открытые вопросы

- **Источник закладок**: откуда берутся (браузерный экспорт? отдельный проект?) и в
  каком формате.
- **Смена модели эмбеддингов** — решена в прототипе (D24: реестр, два хендла
  `embedding`/`search`, сайдкар на модель); открыт вопрос, как это выглядит
  в мобильном клиенте и вторичных устройствах.
- **Другие языки и токенизация**: китайская сегментация, языки помимо ru/en.
- **Правила слияния метаданных** при конфликтах сверх простого объединения.
- **Триггер перехода на Rust/Kotlin** для мобильного пути.

## 15. Журнал решений (ADR)

- **D1.** Всё встраиваемое, без серверов (переносимость, ноль ресурсов в простое).
- **D2.** Результаты выдаются тремя отдельными группами (Личное / Локальное /
  Закладки + web), без сквозного ранжирования между группами.
- **D3.** SQLite — источник правды для метаданных, FTS и тэгов; ANN-индекс — производное.
- **D4.** Эмбеддинги хранятся сайдкарами рядом с источником и реплицируются через Syncthing.
- **D5.** Тэги Obsidian остаются внутри заметок и извлекаются, а не дублируются.
- **D6.** Живая БД никогда не лежит в синхронизируемой папке.
- **D7.** Только open-source компоненты.
- **D8.** Языки: русский и английский обязательны, желательно другие (особенно китайский);
  отсюда — мультиязычная модель эмбеддингов.
- **D9.** Области задаются конфигом: роль папки (`personal` / `foreign` / `web`) задаёт
  группу результатов.
- **D10.** Метаданные элементов — sidecar-файл в формате CSL-JSON + поля Persinder;
  идентификаторы (DOI, ISBN, ISSN, arXiv, PMID) складываются туда же.
- **D11.** Веб — отдельный проект; интерфейс — папка роли `web`.
- **D12.** Дедупликация по хэшу содержимого; отдельная вкладка для ручного сведения копий.
- **D13.** Удаления и правки — инкрементально (`tombstone` + компакция сегментов).
  **Удаление — высокий приоритет, входит в первый прототип.**
- **D14.** Шифрование пока не делаем.
- **D15.** Единственный векторный движок — USearch (LanceDB/DuckDB/EDGEVDB не добавляем).
  *Прототип (модуль 3): USearch уже стоит — индекс `data_dir/ann/<модель>.usearch`
  (косинус, ключи — `id` строк `embeddings`, §8), воркер `embed` его ведёт,
  `ann rebuild` пересобирает; точный скан таблицы остаётся фолбэком и эталоном.*
- **D16.** Внутри группы порядок: точные совпадения → семантика → морфология → тэги.
- **D17.** Базовая модель эмбеддингов — `multilingual-e5-small`; резерв —
  `Qwen3-Embedding-0.6B`.
- **D18.** Чистая архитектура: слои «домен → приложение → адаптеры», зависимости
  направлены внутрь. Модели разделены по слоям — доменные, БД (persistence), HTTP
  (DTO) и внутренние модели сервисов; единый общий `models.py` запрещён (§3.1).
- **D19.** Целевые платформы десктопа — **Windows и Linux** (обе сразу); Android —
  позже. Ядро и хранилища пишутся кроссплатформенно.
- **D20.** Watcher — гибрид: polling-скан (stdlib) — источник правды; `watchdog`
  (опционально) — ускорение реакции. Конфиг областей и watcher — YAML + PyYAML (§6.4).
- **D21.** Состояние watcher'а — **журнал** `data_dir/journal.jsonl` (JSONL,
  append-only): по каждому файлу цепочка статусов
  `discovered → sent → indexed|duplicate|rejected|error` (или `skipped`), `deleted`.
  Журнал — единственный источник состояния (отдельного снапшота нет); незавершённые
  файлы повторяются при следующем запуске. История переходов обрезается до
  `JOURNAL_RETENTION_DAYS` (60 дней), состояние файлов хранится всегда (§6.4).
- **D22.** Сырой текст удаляется **инлайн** там, где документ уходит из индекса:
  при правке вытесненный документ возвращается из `save_document`/`add_source`, при
  удалении — из `IngestService.remove_source`; в обоих случаях текст убирается сразу.
  Владение инвариантом «документ + его текст» — у сервиса `ingest` (у него оба порта:
  `MetaStore` и `TextStore`). Отдельного сборщика мусора нет; брошенное крашем
  (между записью текста и коммитом) подчищает **журнал вызовов ingest**
  `data_dir/ingest.jsonl` (D23).
- **D23.** Ingest ведёт **журнал вызовов** `data_dir/ingest.jsonl` (JSONL,
  append-only, как у watcher'а): намерение *до* опасного шага и итог после
  (`index → indexed`, `duplicate → duplicated`, `remove → removed`, `rejected`).
  На старте сервис сам чистит свой журнал: `IngestService.recover` по незавершённым
  вызовам удаляет брошенные тексты, после чего обрезает историю
  (`INGEST_RETENTION_DAYS`, 60 дней; последняя запись по объекту — всегда).
  Watcher при этом повторно шлёт файлы, по которым нет ответа в его собственном
  журнале (D21). **Все обращения к БД идут через сервис `ingest`** — watcher в
  хранилище напрямую не ходит.
- **D24.** **Сайдкары — производное документа**, и их жизненный цикл повторяет
  текст: пишет воркер `embed` по требованию (`persinder embed`), удаляет `ingest`
  там же, где удаляется текст (владелец инварианта «документ + его текст +
  сайдкары» — прежний D22). Чтобы сайдкар лежал рядом с источником, `ingest`
  получает **абсолютный путь источника** (`IngestRequest.source_path`, он же в
  `embedding_queue` и `document_sources`). Если пути нет — данных на диске нет
  (web, вставленный текст): их сайдкары и сам текст живут в отдельной папке
  `Settings.virtual_dir` (`data_dir/virtual/<модель>/<doc_id>.pdr`). Дубликат с новым
  источником ставит свои задачи в очередь под каждой активной моделью — у каждого
  файла свой сайдкар.
  **Модели управляются явно** (реестр `embed/registry.py`, состояние на профиль
  `data_dir/models.json`): сайдкары — **по подпапке на модель**
  (`.<каталог>/.persinder/<модель>/<файл>.pdr`), чтобы у файла жили эмбеды
  нескольких моделей одновременно. Два хендла: `embedding` (чем считать
  новые/изменённые файлы) и `search` (чем искать). `model install` скачивает веса,
  переключает `embedding` и ставит пересчёт всех источников в очередь — миграция
  стартует при установке, поиск остаётся на старой модели до явного `model use`
  (переключение поиска). Пока хендлы разные, новые файлы индексируются обеими
  моделями. `model remove` удаляет веса и **все сайдкары модели в один момент**
  (не раньше: другие устройства могут быть ещё на старой модели), активным и
  встроенной заглушке — отказ. Эмбеддер подключается через порт `Embedder`:
  реальная e5-small (ONNX INT8, `OnnxEmbedder`) или заглушка `PlaceholderEmbedder` —
  фабрикой `build_embedder(ключ)` по задачам очереди.
