# Задачи

Список согласованных задач и статусов. Обновляется по мере выполнения.
Источники: решения этой сессии + разбросанные по `docs/*.md` и `README.md`.

## Нумерация задач

У открытых задач есть идентификатор `T1…T19` — по порядку появления в файле
(`T1` — самый приоритетный в текущем бэклоге). Правила:

- номер присваивается **один раз** и больше не меняется;
- выполненная задача номер не отдаёт, новая получает следующий свободный —
  даже если по приоритету стоит выше (порядок в списке ≠ номер);
- ссылаемся так: «делай `T3`», «задача `T7`»; в коммитах и ADR — `T3`.

Завершённые итерации ниже называются «Шаг 1/2/3» и `T`-номеров не имеют.

### Шаг 2. `/context` (вариант C: endpoint сам ходит в БД)

- [x] Класс-резолвер текста (`TextResolver` в `api/textresolver.py`):
      - сначала `FsTextStore` (кэш текста, D26) — если текст есть, оттуда;
      - если нет — `SELECT source_path, content_hash, extractor`
        из `document_sources JOIN documents ON id = doc_id`;
      - `source_path` непустой → `ExtractorRegistry.extractor_for(extractor)`
        → `extract(path)` → `Extracted.text`;
      - если ничего нет → ошибка (`source_missing`), которую покажет
        web UI / консоль.
- [x] **Резолвер сам режет текст по символам** (`start`, `end`, `offset`;
      вариант б: раз текст у нас есть — клиент оперирует символами, а не
      байтами) — не тащить весь файл наверх; длинные срезы чанкуются по
      байтовому бюджету, но границы всегда на символах.
- [x] Виртуальные документы (`source_path == ''`): пока отдаём ошибку
      (текст виртуалов в FsTextStore; если его нет — перечитывать нечего).
- [x] `build_fastapi_app` получает `store: MetaStore`, `textstore: TextStore`,
      `registry: ExtractorRegistry | None`, `virtual_dir: Path | None`.
- [x] NDJSON: фрагменты по `CONTEXT_CHUNK_BYTES` (1 МБ), статусы
      `source_missing`/`error`.
- [x] Метод `MetaStore.document_source(doc_id)` — документ + главный источник
      (extractor, content_hash, source_path) для варианта C.
- [x] Тесты: `tests/test_context_api.py` (резолвер, потоки NDJSON,
      интеграция через реальный uvicorn: textstore → перечитывание → ошибки).
      Заодно убран сломанный `threading_model=True` из конфига uvicorn
      (в uvicorn 0.54 такого параметра нет).

## Следующие шаги (после fast_api + /context + /search)

- [ ] **T1. Баг (серьёзный): архивы распаковываются целиком в память** — недопустимо,
      архив может быть любого размера. Все читатели
      (`ArchiveExtractor._read_zip/_read_tar/_read_7z/_read_rar/_read_gz`,
      `sources/extract.py:664-737`) возвращают `list[tuple[str, bytes]]`: **все**
      записи материализуются в RAM целиком. Лимиты анти-бомб
      (`ARCHIVE_MAX_ENTRIES=1000`, `ARCHIVE_MAX_ENTRY_BYTES=32 МБ`,
      `ARCHIVE_MAX_TOTAL_BYTES=64 МБ`) проверяются уже **после** чтения — от OOM
      не спасают. `_read_7z` вдобавок распаковывает весь архив в temp и читает
      каждую запись в память. Для 10-гигабайтного zip это OOM/зависание
      `serve` (watcher и HTTP в одном процессе).
      - Нужно: потоковое чтение **по одной записи** (`zipfile.open`,
        `TarFile.extractfile`), отсечение по `file_size`/`compress_size`
        **до** материализации, не собирать список записей; для 7z/rar —
        поштучное извлечение; `_AreaEntryResolver` сейчас принимает `bytes` —
        перевести на файл/поток (связано с задачей про потоковые экстракторы).
      - Тест: архив с записью > 32 МБ не читается в память (мок `read()`).
- [ ] **T2. Доработка: архивы распаковываются всегда целиком (избыточно)** —
      индексация читает **все** записи и прогоняет классификатор + экстракторы
      по каждой, даже если класс/формат не нужен области; при `--reindex` —
      заново весь архив. Нужно адресное извлечение: пропуск записей по
      имени/расширению до чтения, чтение только нужных, кэш листинга архива
      (names+sizes) на проход.
      - **Что с поиском сейчас:** `/search` архив не открывает вообще (FTS +
        векторы + спаны чанков) — работает штатно.
      - **`/context` на архиве:** пока текст в кэше `pending_texts` — читает
        оттуда и режет по символам. Если кэша нет, `TextResolver` берёт
        `source_path` = `/area/bundle.zip/inner.md` и вызывает
        `extractor.extract(Path(...))` — такого файла на диске нет →
        `FileNotFoundError` → статус `error`. То есть перераспаковки для
        `/context` сейчас **нет**, и части архивов обязаны кэшироваться (D26).
      - Это же даст фолбэк `/context` и воркеру эмбеддингов: адресное чтение
        одной записи вместо полной распаковки.
- [ ] **T3. Доработка: полный путь файла внутри архива** — сейчас `part.name` это
      либо запись верхнего уровня, либо `inner.zip/x.md` (`_nested_parts`,
      глубина **1**), а `source_path` = `<архив>/<part.name>`; в `documents`
      разбор пути не хранится, поэтому «перераспаковать одну запись» нельзя —
      обратный путь неоднозначен (запись с `/`, `name/extractor` при нескольких
      экстракторах, вложенность).
      - Нужно: путь вида `folder/first.zip/folder/second.zip/folder/some.pdf`
        — произвольная вложенность и **явно сохранённый** разбор:
        `container_path` + цепочка `entries: list[str]` (JSON/отдельная таблица
        в `document_sources`). `source_path` остаётся человекочитаемым для UI,
        но не источником истины.
      - Рекурсивное раскрытие вместо глубины 1 (с защитой: лимит глубины,
        суммарного размера, защита от циклов); миграция БД для старых
        документов (best-effort разбор или только кэш).
      - Тесты: архив в архиве в архиве, имена с `/`, несколько экстракторов на
        одну запись, битый вложенный архив.
      - После этого можно снять ограничение «части контейнеров всегда `true`»
        у будущего `is_cachable` (D27).
- [ ] **T4. Кэш текста — единственное хранилище (D26)** — отдельного временного
      хранилища для очереди эмбеддингов **не вводим**: `ingest` пишет текст
      один раз в `pending_texts`, воркер читает его оттуда; кэш живёт, пока
      существует оригинал (D22), виртуальные документы — навсегда.
      - [x] **Фолбэк воркера эмбеддинга** — если файла в кэше нет (крэш,
        ручная чистка, старый профиль): перечитать оригинал экстрактором (как
        `TextResolver` при поиске), сверить `sha256` с
        `documents.content_hash`; не сошлось или перечитать нельзя
        (виртуальный документ, часть контейнера, нет экстрактора/реестра) —
        снять задачи и предупредить в журнале. Кэш — основной путь: спаны
        чанков совпадают без проверок.
      - [ ] **Настраиваемый путь кэша в конфиге** — папка может быть большой,
        её нужно уметь унести на другой диск. Ключ, разрешение путей (`~`,
        относительные от каталога конфига), миграция старой
        `<home>/pending_texts` — **решение не принято** (пользователь пока не
        ответил). Сюда же: `embed` и `search --local` конфиг сейчас не читают.
      - [ ] **Имя** — оставить историческое `pending_texts` (теперь это кэш)
        или переименовать в `text_cache`/`texts` с миграцией.
      - **Не нужно:** двух записей в `ingest`, удаления после эмбеддингов,
        sweep «протёкшего» temp — temp нет.
- [ ] **T5. `is_cachable()` в протоколе экстрактора (D27)** — экстрактор сам решает,
      копировать ли его текст в `pending_texts` (`true` — копируем, `false` —
      нет). Идея принята, реализация **отложена**: первый же вопрос вскрыл
      связки, которые надо решить до кода.
      - **Нет текста → нет эмбеддингов.** В D26 воркер уже умеет фолбэк на
        оригинал, поэтому `false` теперь означает «текст не хранится на диске
        вообще»: воркер перечитывает оригинал и сверяет хэш, `/context` — тоже
        перечитывает. Вопрос: ставить ли в очередь эмбеддинги при `false` или
        считать такой формат «без семантики».
      - **Части контейнеров всегда `true`.** Их `source_path` —
        `arch.zip/inner.md`, на диске такого файла нет: ни `/context`, ни
        фолбэк воркера перечитать не могут.
      - **Сверка на старте.** `reconcile.py:110` забывает запись журнала,
        если текста нет («сырой текст потерян») → некэшируемый файл будет
        переиндексироваться при каждом запуске. Нужен флаг в `documents`
        (например, `text_cached`), иначе `--reindex` каждый раз перечитывает
        такие файлы целиком.
      - **Виртуальные документы** (`source_path == ''`, web/вставка) —
        кэшируются всегда: другого места для их текста нет.
      - **Где живёт решение** — `is_cachable() -> bool` без аргументов
        (свойство формата) или `is_cachable(path)` (по конкретному файлу);
        решает листовой экстрактор, у `ContainerExtractor` метода нет.
      - **Дефолт** — `true` (обратная совместимость).
- [ ] **T6. Сжатие zip текста в FsTextStore** — хранить текст сжатым, а не
      разжатым UTF-8.
- [ ] **T7. Потоковый интерфейс экстракторов** — если формат файла поддерживает,
      извлекать только нужный байтовый диапазон, не распаковывая весь файл
      в память.
