# Производительность и конкурентность поиска

> Замеры сделаны 2026-11-11 на реальном сервере (`persinder serve`, dev-корпус,
> модель e5-small-int8-v1, ONNX CPU). Ветка `feature/web-ui`, коммиты
> `897efa8` (numpy-скан), `956ef4f` (кэш эмбеддера), `9945f49` (лок кэша).

## 1. Модель конкурентности

HTTP-слой — `ThreadingHTTPServer` из стандартной библиотеки (`http.py`):
**каждый запрос обслуживается в собственном потоке**, N одновременных клиентов
= N потоков. Потоки демоны (`daemon_threads = True`): разрыв соединения
клиентом не держит процесс.

Почему так: сервис локальный (слушает только `127.0.0.1`) и персональный.
Полноценный веб-стек (`uvicorn`/`fastapi`, extra `http`) — запасной путь,
если когда-нибудь понадобятся сотни запросов/с (см. §4).

## 2. Что безопасно при N одновременных запросах

| Узел | Механизм | Вывод |
|---|---|---|
| `SqliteStore` | все операции под `threading.RLock` | запросы сериализуются, гонок нет |
| эмбеддер (`OnnxEmbedder`) | одна ONNX-сессия на процесс; `session.run` и токенизатор потокобезопасны; кэш в `VectorSearch._embedder` **под локом** | модель строится один раз, остальные потоки ждут |
| ANN-индекс USearch | каждый запрос открывает свой mmap-экземпляр на чтение | безопасно |
| точный скан | локальные numpy-массивы, общих данных нет | безопасно |
| `FsTextStore` (контекст) | независимые чтения файлов | безопасно |

**Почему эмбеддер один на всех:** создание эмбеддера стоит ~1.4 с
(токенизатор + ONNX-сессия + warmup-прогон). Раньше `build_embedder`
вызывался на каждый запрос — каждый символ в строке поиска платил секунды.
Теперь экземпляр создаётся один раз на процесс и переиспользуется всеми
потоками; `embed_query` после загрузки — единицы миллисекунд.

## 3. Замер нагрузки

Методика: N потоков бьют `GET /search?q=…&limit=5` (реальный поиск: морфология
+ семантика + контекст), 5 запросов на поток. Машина: 2 ядра, ~7.8 ГиБ RAM.

| N клиентов | ошибок | запросов/с | медиана | p95 |
|---|---|---|---|---|
| 1 | 0 | — | 20 мс | 1.5 с\* |
| 4 | 0 | 90 | 41 мс | 76 мс |
| 16 | 0 | 84 | 173 мс | 303 мс |
| 32 | 0 | 69 | 261 мс | 1.5 с |

\* — разовая загрузка модели на **первом** запросе процесса. Раньше эта цена
платилась на каждый запрос (см. §2).

Выводы:

- **Корректность не страдает** вплоть до 32 одновременных клиентов: 0 ошибок,
  все ответы валидны.
- Задержка растёт с конкуренцией: сериализация на DB-лок + борьба за CPU.
- Пропускная способность держится ~70–90 запросов/с — потолок 2-ядерной
  машины. Для личного поиска это с запасом.
- Сервис слушает только `127.0.0.1`: «N клиентов» — это свои же вкладки и
  устройства, а не внешний трафик.

## 4. Дальнейшие направления

- **Больше запросов/с** — перейти с `ThreadingHTTPServer` на `uvicorn`
  (extra `http` уже есть в зависимостях); локальность сервиса пока не требует.
- **Прогрев при старте** — загрузить эмбеддер не на первом запросе, а при
  запуске `serve`, чтобы убрать разовый всплеск 1.5 с из «первой» задержки.
- **Память скана** — точный скан держит матрицу `N × dim` float32 (~45 МБ на
  30k чанков); для сотен тысяч чанков — обрабатывать блоками.
